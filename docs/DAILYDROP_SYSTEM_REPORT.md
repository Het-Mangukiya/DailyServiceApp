# DailyDrop System Report

Prepared on 2026-04-10 from direct source inspection of the project codebase. This report was compiled by exploring the actual implementation in `app/`, `functions/`, `tests/security/`, `scripts/`, `.github/workflows/`, `firestore.rules`, `firestore.indexes.json`, and the Android resource structure, rather than relying on README summaries.

## 1. Project Introduction

DailyDrop is a native Android application for recurring local service businesses and their customers. The app is designed for daily service workflows where a provider regularly delivers or completes a service for multiple customers and needs one system to manage:

- customer records
- daily completion tracking
- billing and ledger calculation
- payment collection
- customer-provider linking
- complaints and support tickets
- quantity change requests
- route planning
- notifications
- business reports

The current implementation supports service types such as milk, newspaper, water, tiffin, laundry, maid services, and similar repeat-delivery or repeat-service businesses.

## 2. Product Goal

The main goal of DailyDrop is to digitize the full operating cycle of a daily service provider.

Instead of tracking deliveries manually, keeping outstanding balances in notebooks, and handling customer complaints through scattered calls or messages, DailyDrop brings the whole workflow into one mobile-first system. It is built to help providers run their day faster and help customers stay informed about their service status, payments, requests, and support issues.

## 3. Primary Users

### Provider

The provider is the main business operator. The provider can:

- create and manage customer records
- complete daily service entries
- review billing and ledger summaries
- record customer payments
- handle join requests from customers
- approve or reject extra quantity requests
- review and resolve support tickets
- generate QR codes and invite links
- optimize delivery routes
- view performance reports and prediction insights

### Customer

The customer can:

- sign up and log in
- link with a provider using code, QR, or invite link
- view active service details
- see summary, ledger, and payment information
- request extra quantity
- raise complaints or support tickets
- receive notifications about service-related actions

### Platform Maintenance Scope

The project includes backend, security, and maintenance utilities for:

- Firestore rules enforcement
- notification dispatch
- quality checks
- one-time ownership correction scripts

There is a shared `ADMIN` role constant in the codebase, but the current visible product flow is centered mainly on `PROVIDER` and `CUSTOMER`.

## 4. End-to-End Product Flow

### 4.1 App Startup and Routing

The launcher entry is `SplashActivity`. It performs branded splash animation and then routes the user based on saved session state, role, invite token, and provider profile readiness.

Startup routing covers:

- logged-out users go to `LoginActivity`
- logged-in providers are checked for profile completeness before entering the dashboard
- logged-in customers are routed based on active provider link state
- invite deep links are captured and claimed through `customerInvites`
- customers with an active linked provider are sent directly to `CustomerServiceDashboardActivity`
- customers without an active link are sent to `CustomerHomeActivity`

This makes the splash flow more than a visual screen. It is the role-aware entry controller for the entire application.

### 4.2 Authentication and Account Entry

The app supports:

- email and password login
- email and password sign-up
- Google Sign-In
- forgot password flow
- persistent session storage through preferences

User identity is stored in Firebase Authentication, while role and profile metadata are stored in Firestore under the `users` collection and related domain collections.

### 4.3 Provider Onboarding

After sign-up or login, a provider is required to complete the business profile if mandatory information is missing. The profile flow is handled by `ProfileActivity`.

Provider profile data includes:

- business name
- owner name
- phone
- email
- address
- area and city
- GST
- UPI ID
- service notes
- supported service categories

This ensures the provider enters the operational part of the app only after a minimum business setup is complete.

### 4.4 Customer Linking and Activation

Customers can connect to a provider through three main paths:

- entering a provider code manually
- scanning a QR code generated by the provider
- opening an invite deep link

The linking lifecycle is built around `customerLinks` and `customerInvites`.

The implemented flow includes:

- customer discovers or scans provider
- join request is created
- provider reviews pending requests in `JoinRequestsActivity`
- provider approves or rejects the request
- active link is created or updated
- customer is routed to the active service dashboard

This creates a controlled relationship model instead of allowing open access to provider data.

### 4.5 Daily Service Operations

The provider’s core operational workflow is handled through `ServiceEntryActivity`.

This module lets the provider:

- load active customers
- select a service date
- mark deliveries or service completion in batch
- work with cached customer data when offline
- queue pending entries locally when network is unavailable
- sync pending entries later through WorkManager

This is one of the strongest operational parts of the project because it supports real daily usage, including weak-network conditions.

### 4.6 Billing, Ledger, and Payments

DailyDrop converts repeated service activity into monthly financial tracking.

Implemented billing and finance flow includes:

- service entries stored per provider and customer
- bill list and bill detail screens
- customer ledger summary calculation
- payment recording through `PaymentActivity`
- payment methods such as cash, UPI, bank transfer, cheque, and other
- outstanding balance calculation from service totals versus payments
- monthly PDF generation using `MonthlyBillPdfGenerator`
- summary sharing from the customer service dashboard

This gives the app a complete loop from service completion to money collection.

### 4.7 Customer Self-Service

Once linked, the customer enters `CustomerServiceDashboardActivity`, which acts as the customer portal.

The customer can:

- view provider and service context
- see monthly summary and ledger details
- inspect payments
- request extra quantity
- raise complaints
- export or share monthly summary

This transforms the customer from a passive recipient into an active participant in the service process.

### 4.8 Complaints and Support

The complaint system is implemented through:

- `ComplaintSupportActivity` on the customer side
- `ProviderComplaintsActivity` on the provider side

The support workflow includes:

- category-based complaint creation
- ticket status handling such as `OPEN`, `IN_PROGRESS`, and `RESOLVED`
- provider-side review and updates
- explicit email action when the user chooses to contact the other side
- notification creation for relevant changes

This gives the project a proper issue-resolution channel instead of relying only on external messaging apps.

### 4.9 Extra Quantity Requests

Customers can request an increase or change in service quantity from `CustomerServiceDashboardActivity`.

Provider handling is done in `QuantityRequestsActivity`, where the provider can:

- review pending requests
- approve or reject requests
- send the result back as a notification event

This is a very practical feature for subscription-style or repeat-quantity businesses.

### 4.10 Notifications and Awareness

The project includes an in-app and mobile notification system built around the `notifications` collection.

Current notification stack includes:

- `NotificationListActivity` for inbox-style history
- `NotificationHelper` for notification creation and local display
- `NotificationSyncManager` for real-time Firestore listening and local notification triggering
- `FCMService` for Firebase Cloud Messaging receive and token updates
- optional Cloud Function trigger in `functions/index.js` for server-side push delivery

Notification usage covers flows such as:

- join requests
- quantity requests and decisions
- complaint updates
- customer-provider relationship events
- payment-related or service-related alerts

The architecture supports in-app visibility and live notifications, with cloud-triggered push available when Firebase Functions is deployed.

### 4.11 Route Planning and Delivery Navigation

The application includes two route-focused experiences:

- `DeliveryRouteActivity` for simple ordered stop handling
- `RouteOptimizationActivity` for more advanced route planning and reordering

Available actions include:

- sorting customers by area and address
- drag-and-drop stop reordering
- opening a multi-stop route in Google Maps
- direct call action for customers from the route list

This extends the product beyond record-keeping into actual daily execution support.

### 4.12 Reports and Prediction

Business visibility is handled through:

- `ReportsActivity` for historical reporting and charts
- `SalesPredictionActivity` for prediction-driven insights from an external API

Reports include:

- total revenue
- deliveries
- customers
- payments
- overdue bills
- service distribution
- top customers
- visual charts using MPAndroidChart

The prediction screen adds a more advanced layer by consuming a remote service to show forecasted sales-oriented insight.

### 4.13 QR and Sharing Utilities

The app includes provider-side QR generation through `QRCodeActivity`.

This feature allows:

- provider code generation
- QR display
- QR sharing
- QR image saving via `FileProvider`

Combined with invite links and manual codes, this gives the app a flexible customer acquisition and linking system.

### 4.14 AI and Data Export Utility

The class `AITrainingDataGenerator` shows that the project also contains a data export capability for converting support ticket data into JSONL format for AI training or analytics preparation.

This is not just a consumer-facing feature. It also signals a forward-looking utility layer for internal intelligence workflows.

## 6. Technical Architecture

### 6.1 Mobile App Layer

The Android app is built primarily in Java with modern Android libraries and patterns.

Key implementation choices:

- native Android activities and XML layouts
- Hilt for dependency injection
- Firebase Authentication for identity
- Cloud Firestore for real-time data
- Firebase Storage and Messaging integrations
- Room database for local customer caching
- WorkManager for background synchronization
- Retrofit and OkHttp for external API communication
- MPAndroidChart for reporting charts
- ZXing for QR scanning
- Android PDF APIs for bill export

### 6.2 Backend and Cloud Layer

The backend is centered on Firebase services.

Main backend components:

- Firestore as the operational database
- Firestore security rules for access control
- Firestore composite indexes for high-value queries
- Firebase Messaging for push infrastructure
- Cloud Function `sendPushNotification` for notification fan-out when functions are enabled

### 6.3 UI and UX Layer

The codebase now includes:

- branded splash motion
- centralized container animation through `PremiumMotionController`
- edge-to-edge toolbar inset handling in `BaseActivity`
- RecyclerView row animations
- button and card press feedback

This creates a more polished mobile experience across the app rather than isolated one-off animations.

## 7. Data Model and Firestore Design

The main Firestore collections currently in use include:

| Collection | Purpose |
|---|---|
| `users` | Auth-linked profile metadata and role information |
| `providers` | Provider business profile and setup data |
| `customers` | Provider-owned customer records |
| `customerLinks` | Active or pending relationship between customer accounts and providers |
| `customerInvites` | Secure invite-link claim workflow |
| `serviceEntries` | Daily service completion records |
| `bills` | Bill records and billing context |
| `payments` | Payment records against customers and bills |
| `supportTickets` | Complaint and support history |
| `quantityRequests` | Customer extra quantity request lifecycle |
| `notifications` | In-app notification inbox and notification event stream |

Important architectural observations:

- provider ownership is central to data design
- most business records are filtered by `providerId`
- customer account access is controlled through `customerLinks`
- notifications are persisted, not just displayed transiently
- indexes exist for key operational queries on customers, service entries, payments, bills, and notifications

## 8. Offline, Sync, and Reliability Design

One of the strongest engineering aspects of the project is its offline-aware delivery workflow.

Implemented offline behavior includes:

- Room-based customer cache
- pending service entry queue in local storage
- background retry through `PendingEntriesSyncWorker`
- periodic scheduling through `SyncWorkScheduler`
- graceful operation even when delivery is marked offline first and synced later

This is especially valuable for providers working in the field where connectivity may be inconsistent.

## 9. Security Model

The application includes a meaningful security layer through Firestore rules and automated rules tests.

Security design covers:

- users can access only their own profile data where appropriate
- providers can only operate on their own customers and related business records
- customers can only access link data and support flows related to their own relationship
- immutable ownership checks on sensitive collections
- delete restrictions on support tickets and non-owned resources
- collection-level protections for payments, bills, service entries, and links

The repository also includes emulator-based automated rules tests in `tests/security/` that verify:

- provider ownership enforcement
- customer access boundaries
- anonymous access denial
- mutation restrictions on provider-owned resources
- support ticket update constraints

This gives the project stronger backend confidence than a UI-only application.

## 12. Current Boundaries and Practical Notes

The current implementation also has some practical boundaries that are important to understand:

- this is an Android-first product; no iOS or web client was found in the repository
- server-side notification fan-out depends on Firebase Functions being deployed
- the prediction feature depends on an external API endpoint
- the admin role is defined in shared constants, but the primary shipped flow is provider and customer oriented
- offline support is strongest around service entry and customer caching, not every possible module

These are not weaknesses by themselves. They simply define the current stage and scope of the product.
